# Kubernetes Init Containers Practice

This repository demonstrates the practical usage and lifecycle of **Init Containers** vs **Regular Application Containers** in a multi-node Kubernetes cluster.

---

## 📌 Architecture Overview

The deployment provisions a two-replica Nginx web server using a custom lifecycle strategy:

1. **`wait-for-db` (Init Container 1):** Simulates a dependency check (e.g., waiting for a database service to become available) before running the application.
2. **`fetch-config` (Init Container 2):** Generates/fetches dynamic HTML configuration content and stores it inside a shared `emptyDir` volume.
3. **`web-app` (Main Container):** An Nginx web server that mounts the shared volume and serves the HTML generated by the init stage.

---

## 🛠️ Kubernetes Manifest (`task-of-init-pod.yaml`)

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: production-demo-app
  labels:
    app: demo-web
spec:
  replicas: 2 # Deploy pods on the worker nodes
  selector:
    matchLabels:
      app: demo-web
  template:
    metadata:
      labels:
        app: demo-web
    spec:
      # Shared Volume to transfer data between the Init and App container
      volumes:
      - name: config-volume
        emptyDir: {}

      # ----------------------------------------------------
      # 1. INIT CONTAINERS (Executed sequentially)
      # ----------------------------------------------------
      initContainers:
      # Init 1: Wait for database to be ready
      - name: wait-for-db
        image: busybox:1.36
        command: ['sh', '-c', 'echo "Checking Database connection..."; sleep 10; echo "DB is READY!"']

      # Init 2: Write the config file into the shared volume
      - name: fetch-config
        image: busybox:1.36
        command: ['sh', '-c', 'echo "<h1>Welcome from Production App - Config Loaded via InitContainer</h1>" > /work-dir/index.html']
        volumeMounts:
        - name: config-volume
          mountPath: /work-dir

      # ----------------------------------------------------
      # 2. MAIN APP CONTAINER (Runs only after all inits succeed)
      # ----------------------------------------------------
      containers:
      - name: web-app
        image: nginx:alpine
        ports:
        - containerPort: 80
        volumeMounts:
        - name: config-volume
          mountPath: /usr/share/nginx/html # Replace main page with the file created by Init Container
```

## 🚀 Execution & Verification Steps

### 1. Apply the Deployment Manifest
```bash
kubectl apply -f task-of-init-pod.yaml
```

### 2. Monitor Pod Lifecycle Transition
```bash
kubectl get pods -w
```

**Expected Transition States:**
- `Pending` $\rightarrow$ Pod scheduled on worker node.
- `Init:0/2` $\rightarrow$ Executing `wait-for-db`.
- `Init:1/2` $\rightarrow$ Executing `fetch-config`.
- `PodInitializing` $\rightarrow$ Init phase complete, initializing `web-app`.
- `Running (1/1)` $\rightarrow$ App container is active and serving traffic.

---

### 3. Verify Container Logs

* Check logs for the first init container:
  ```bash
  kubectl logs -l app=demo-web -c wait-for-db
  ```
  **Output:**
  ```text
  Checking Database connection...
  DB is READY!
  ```

* Check logs for the second init container:
  ```bash
  kubectl logs -l app=demo-web -c fetch-config
  ```
  *(Note: Output is empty because output was redirected directly into `/work-dir/index.html` file).*

---

### 4. Verify Shared Volume Content Inside Main Container

Execute a command in the main `web-app` container to check if the file created by the `fetch-config` init container was successfully mounted:

```bash
kubectl exec -it deployment/production-demo-app -c web-app -- cat /usr/share/nginx/html/index.html
```

**Output:**
```html
<h1>Welcome from Production App - Config Loaded via InitContainer</h1>
```

---

## 🔑 Key Takeaways
- **Sequential Execution:** Init containers always run one after another in the order they are defined.
- **Completion Mandate:** All Init containers must exit with status `0` before the main application container starts.
- **Data Sharing:** Data prepared during initialization can easily be shared with the application container using `emptyDir` volumes.
